# Manual cleanup — 2026-10-28

A hands-on cleanup session on a 250 GB Mac that had run out of space even
after running `cleaner.py`. It took free space from **358 MB to 79 GB**.
This document records what was found, what the cleaner missed, and the
lessons to carry into the next cleanup and into the cleaner itself.

## Where the space was really going

The question was *"why does macOS take 200 GB?"* It doesn't. macOS itself
(System + Preboot + Recovery + VM/swap volumes) was **~22 GB**. Everything
else was user data that macOS's Storage panel lumps into **"System Data"**
because it lives in hidden folders:

- `/private/var/folders/zz/…/com.apple.SoftwareUpdate/` — **28 GB** of
  half-finished macOS installer downloads from 2024 that Software Update
  never cleaned up. The single biggest item, and invisible without `sudo`.
- `/System/Library/AssetsV2/com_apple_MobileAsset_iOSSimulatorRuntime/` —
  iOS Simulator runtimes, ~8–10 GB each.
- `~/Library/Application Support/<App>` and `~/Library/Containers`,
  `~/Library/Group Containers` — data from apps that had long been
  uninstalled (dragging an app to the Trash leaves all of this behind).

## What `cleaner.py` missed (candidate detectors)

1. **Stale `InstallAssistant.pkg.partial` files** in
   `/private/var/folders/*/*/C/com.apple.SoftwareUpdate/`. Root-owned, so the
   cleaner can only *report* them and print the `sudo` command. Use an age
   filter (`-mtime +300`) so an in-progress download is never touched.
2. **Orphaned app data.** Match each folder in `Application Support`,
   `Containers`, `Group Containers`, `Preferences`, `HTTPStorages` against
   bundle IDs/names of apps in `/Applications` and `~/Applications`, plus
   CLI tools on `PATH`. Anything with no owner is a candidate.
   Group Container names are opaque (`JQ525L2MZD.pepe` was Photoshop
   Elements) — look at the `.plist` names inside to identify the owner.
3. **iOS runtime files left behind after `simctl runtime delete`.** See
   *Open items*. The README's claim that `simctl runtime delete` is the way
   to remove a runtime is only half true: it unregisters the runtime but
   left 16.6 GB of `.asset` folders on disk.
4. **Stalled installers**, e.g. `~/Library/Application Support/com.docker.install/in_progress`.
5. **Update staging caches**: `~/Library/Caches/com.microsoft.VSCode.ShipIt`.
6. **Old copies of VS Code extensions**: two versions of the same
   extension side by side; only the highest version is in use.

## Process that worked

- **Measure before proposing.** `df -h`, `diskutil apfs list`,
  `du -xhd1` level by level. Account for every GB before deleting anything.
- **Admin scans via a script the user runs.** The agent can't type the sudo
  password, so it writes a read-only script (only `du`/`find`/`sort`) to a
  scratch folder, the user runs `sudo bash script.sh`, and the script writes
  its results to a file the agent reads. Same pattern for root-only deletes:
  give one exact, narrowly filtered command.
- **One section at a time, each approved explicitly**, with a table of
  path, size, and impact on the dev stack, and what is being *kept* and why.
- **Verify after every delete**: re-check that the paths are gone, the kept
  tools still work (`which claude`, `xcrun simctl runtime list`), and the
  new free space.

## Dependency checks before deleting dev tooling

Never decide from size alone. Check what actually uses it:

| Before deleting… | Check |
|---|---|
| Gradle versions in `~/.gradle/wrapper/dists` and `~/.gradle/caches/<ver>` | `find <projects-dir> -name gradle-wrapper.properties` and see which projects use which version |
| Android NDKs | `grep ndkVersion` in each `android/app/build.gradle*`, plus Flutter's default in `flutter_tools/.../FlutterExtension.kt` |
| Android system images | Each AVD's `image.sysdir.1` in `~/.android/avd/*.avd/config.ini` |
| Android emulators | Always keep at least one |
| iOS runtimes | Keep the highest version; `xcrun simctl list devices` |
| `~/gitlab-runner` | `pgrep -lf gitlab-runner`; if the runner is live, leave it |
| Docker | `executor` in `~/.gitlab-runner/config.toml` (here: `shell`, so CI did not need Docker); `Dockerfile` / `docker-compose.yml` in projects |
| CoreSimulator dyld cache | Its folder name is a macOS build number; compare with `sw_vers`. Matching means it's current and will just regenerate |

## Gotchas

- **SIP "restricted" folders can't be deleted, even with `sudo`.** Check with
  `ls -ldO <path>`; `restricted` in the flags column means only Apple's own
  services can remove it.
- **`.com.apple.containermanagerd.metadata.plist`** keeps empty
  `~/Library/Containers/<app>` shells alive ("Operation not permitted").
  The data inside does get deleted; the ~50 KB shell is harmless.
- **`du` without `-x` crosses into mounted simulator volumes**
  (`/Library/Developer/CoreSimulator/Volumes/…`) and makes `/Library`
  look 14 GB bigger than it is.
- **Docker's virtual disk (`Docker.raw`) reports 250 GB** but is sparse.
  `du` shows its real usage (~4 GB here).
- **Docker's uninstaller** (`/Applications/Docker.app/Contents/MacOS/uninstall`)
  removes the VM and its helpers but leaves `Docker.app`, `~/.docker`, and
  some prefs. Delete those afterwards.
- **`code --uninstall-extension`** only marks extensions as removed until
  VS Code restarts; delete the folders too. It also refuses to uninstall an
  extension another one depends on (`vscode-containers` before `docker`), so
  order matters.
- **Extension IDs aren't always obvious.** `openai.codex-audio` came bundled
  with `openai.chatgpt` and went with it.
- **macOS Settings vs `df`**: Settings uses decimal GB and counts the system
  volumes, so "172 GB used" there ≈ 141 GiB used on the Data volume plus
  ~22 GB of macOS.
- **Rescue user files first.** Word's container held an unsaved
  `AutoRecovery save of …docx`; it was copied to `~/Downloads` before the
  container was deleted.

## Open items

- **16.6 GB of iOS 18.1 / 18.2 runtime files** remain in
  `/System/Library/AssetsV2/com_apple_MobileAsset_iOSSimulatorRuntime/`
  (one `<hash>.asset` folder per runtime; the version is in each folder's
  `Info.plist`, e.g. `plutil -extract MobileAssetProperties.SimulatorVersion raw <hash>.asset/Info.plist`).
  Protected by SIP, so `sudo rm` fails.
  Next: check after a restart whether macOS cleans them up; otherwise try
  Xcode → Settings → Components. Once a working method is found, fix the
  cleaner's runtime removal to use it.
- **Norton** (~1.9 GB): remove with `/Applications/com.norton.av.uninstaller.app`
  (needs a restart), then sweep for Symantec/Norton leftovers in
  `/Library/Application Support`.
- **Optional**: `flutter clean` in the large active Flutter project (3.8 GB of
  `build/` + `.dart_tool/`).
